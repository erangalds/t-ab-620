## 1. Core Architecture & Concepts

* **Question-and-Condition Node Coupling:**
* When an **Ask a question** node is created using the **Multiple choice options** entity extraction type, Copilot Studio automatically constructs a parallel branching tree via a downstream **Condition** node.
* Each distinct option defined in the question node instantiates a dedicated deterministic conditional branch (`If condition is met`).
* A default terminal catch-all branch—**All other conditions** (`Else`)—is pinned permanently to the far right of the condition block to handle input mismatches or unhandled choices.


* **Slot Filling & Conversational Memory:**
* When asking a question, Copilot Studio attempts entity recognition and extraction to bind the user's input into a strongly typed variable.
* **Question Skipping (Pre-Slot Filling):** If a target variable has already been resolved in memory (e.g., passed in from an initial utterance or upstream node), the runtime can bypass the node automatically without re-prompting the user.


* **Variable Architecture & Scoping Hierarchy:**
* **Topic-Level Scope (`Topic.<VariableName>`):** The variable's lifecycle and memory allocation are isolated strictly to the execution boundary of the active topic dialog. Sub-topics, sibling topics, and parent topics cannot read or mutate this variable unless explicitly passed via topic redirection input/output parameters.
* **Global-Level Scope (`Global.<VariableName>`):** The variable is promoted to global bot memory, persisting across multiple topics and turns throughout the user's session.
* **Variable Sensitivity Masking:** Marking a variable as sensitive prevents raw parameter values from being surfaced in diagnostic execution logs, session transcripts, or telemetry pipelines (essential for PII/compliance such as phone numbers, emails, national IDs).
* **Session Persistence:** Determines whether variable values survive context resets or persist between independent conversational sessions across supported channels.


* **Entity Extraction Foundations:**
* **Multiple Choice Options:** A closed list of literal text values configured inside the node. Maps automatically to a specialized local choice/option set variable.
* **Prebuilt Entities:** Out-of-the-box system regex and machine learning extractors (e.g., `Age`, `City`, `Color`, `Date and time`, `Event`, `Language`, `Person name`, `Phone number`).
* **Custom Entities:** Maker-defined Closed Lists (with synonyms) or Regular Expression (RegEx) entities.
* **User's Entire Response:** Captures raw, unparsed string text directly without entity filtering; stores the value as a primitive `String` data type.


* **Deterministic Evaluation Order (Short-Circuit Evaluation):**
* Conditional branches are evaluated sequentially from **left to right**.
* The first condition evaluating to `true` executes its sub-canvas branch immediately; all subsequent sibling conditions are bypassed (short-circuited).
* If no conditional branch evaluates to `true`, execution drops into the far-right **All other conditions** branch.


* **Canvas Convergence:**
* After executing the specific nodes within an activated condition branch, all disparate branches converge back into a single unified execution thread beneath the condition block. Shared downstream actions can continue from that merged anchor node.

## 2. Platform Features & Capabilities

* **Question Node Configuration (`Ask a question`):**
* **Prompt Text:** Accepts rich text formatting (bold, italic, numbered lists, bullet points), media additions (files, images, videos), Basic Cards, Adaptive Cards, Quick Replies, and variable insertion (`{X}`).
* **Identify Dropdown:** Configures the entity extraction model. Options include *Multiple choice options*, *List variable*, *User's entire response*, prebuilt system entities, or custom entities.
* **Options for User:** Visual list input. Each entered string requires pressing **Enter** to commit the choice token. The visual canvas shifts dynamically to generate matching downstream condition branches.
* **Save Response As:** Clickable variable chip (defaults to autogenerated names like `var1`).
* Configurable fields: Variable name (renamed to `employeeName`), Variable Scope (*Topic* vs. *Global*), Data type (e.g., `Choice`, `String`), and *Sensitive data* masking toggle.




* **Question Behavior Properties Pane (Ellipsis `...` $\rightarrow$ Properties):**
* **Skip Question Configuration:**
* *Ask every time:* Node executes unconditionally whenever reached.
* *Skip if value exists:* Node checks if the target variable is non-null. If already populated, the question prompt is suppressed and execution continues to the next node.


* **Reprompt / Retry Logic (Invalid Answers):**
* Controls behavior when the user's utterance fails entity extraction validation (e.g., user supplies non-numeric text for an age entity).
* Configurable retry thresholds: *Don't repeat*, *Repeat once*, or *Repeat twice*.
* Fallback action after retries exhausted (e.g., proceed with empty variable or redirect to Fallback).


* **Interruption Handling:**
* Toggle: *Allow customer to switch to another topic during this action*. Controls whether global intent recognition / NLU can interrupt the question flow to launch a new topic.




* **Condition Node Operations (`Add a condition`):**
* **Branch Management:** Click the ellipsis (`...`) on individual condition cards to *Insert condition left/right*, *Delete*, or *Move (reorder)* left/right. The *All other conditions* branch cannot be deleted or reordered.
* **Rule Engine Comparison Operators:**
* Text/Choice: `is equal to`, `is not equal to`, `is blank`, `is not blank`.
* Numeric: `is greater than`, `is less than`, `is greater than or equal to`, `is less than or equal to`.


* **Formula Conversion:** Individual condition cards can be converted directly into raw **Power Fx formulas** via the ellipsis menu (`Change to formula`).


* **Test Canvas & Tracing Diagnostics:**
* **Visual Trace Execution:** When testing inputs, green tracking outlines trace active branches in real time.
* **System Fallback Redirection:** Utterances failing NLU trigger thresholds trigger the system topic `Fallback` (e.g., *"I'm sorry, I'm not sure how to help with that. Can you try rephrasing?"*).
* **Variable Injection in Output Messages:** Variables can be referenced directly within message text nodes via the `{X}` variable picker, printing the dynamic runtime value inline (e.g., `Topic.employeeName`).

## 3. Formulas, Expressions & Schemas

### Topic Definition Schema (Bot Component YAML Representation)

The declarative YAML representation of the question node, variable binding, choice entity extraction, and multi-branch condition block is structured as follows:

```yaml
kind: AdaptiveDialog
beginDialog:
  kind: OnRecognizedIntent
  id: main
  intent:
    displayName: Leave allowance
    triggerQueries:
      - how much leave time do I have?
      - how can I find out how much vacation allowance I have?
      - am I able to take sick leave in this job?
      - what holiday time can I take in a year?
      - do I have both holiday and sick leave?

  actions:
    - kind: Question
      id: question_employeeName
      variable: init:Topic.employeeName
      prompt: Which employee are you interested in knowing their leave allowance?
      entity:
        kind: EmbeddedChoiceEntity
        choices:
          - value: Philip
          - value: Jane
          - value: Maria
          - value: Susan
          - value: other

    - kind: ConditionGroup
      id: conditionGroup_leaves
      conditions:
        - id: cond_philip
          condition: =Topic.employeeName = 'Topic.employeeName'.Philip
          actions:
            - kind: SendMessage
              id: msg_philip
              message: Philip has 30 vacation days and 5 sick days per year.

        - id: cond_jane
          condition: =Topic.employeeName = 'Topic.employeeName'.Jane
          actions:
            - kind: SendMessage
              id: msg_jane
              message: Jane has 34 vacation days.

        - id: cond_maria
          condition: =Topic.employeeName = 'Topic.employeeName'.Maria
          actions:
            - kind: SendMessage
              id: msg_maria
              message: Maria has 35 vacation days.

        - id: cond_susan
          condition: =Topic.employeeName = 'Topic.employeeName'.Susan
          actions:
            - kind: SendMessage
              id: msg_susan
              message: Susan has 29 vacation days and 4 sick days.

        - id: cond_other
          condition: =Topic.employeeName = 'Topic.employeeName'.other
          actions:
            - kind: SendMessage
              id: msg_other
              message: You might want to confirm that {Topic.employeeName} has the standard allowance.

      elseActions:
        - kind: SendMessage
          id: msg_default
          message: You might want to confirm that {Topic.employeeName} has the standard allowance.

```

### Power Fx Condition Formulas

When converting standard UI condition builders into Power Fx expressions, the underlying evaluation logic executes as:

```powerfx
// Exact match against Choice entity value
Topic.employeeName = 'Topic.employeeName'.Philip

// Power Fx evaluation for handling "Other" or blank conditions
Topic.employeeName = 'Topic.employeeName'.other || IsBlank(Topic.employeeName)

// String comparison alternative (if User's Entire Response is used instead of Choice)
Lower(Trim(Topic.employeeName)) = "philip"

```

### Power Fx String Interpolation in Message Nodes

Dynamic runtime evaluation of message text embedding variable values:

```powerfx
// Evaluated expression executed when sending fallback/standard allowance message
Concatenate(
    "You might want to confirm that ",
    Text(Topic.employeeName),
    " has the standard allowance."
)

```

## 4. Best Practices & Design Patterns

* **Semantic Variable Naming:**
* Avoid default autogenerated variable labels (e.g., `var1`, `var2`). Rename variables immediately upon creation to reflect their business payload (e.g., `Topic.employeeName`, `Global.TargetEmployeeId`).


* **Variable Scope Minimization (Principle of Least Privilege):**
* Keep variables scoped to **Topic** level by default. Only promote variables to **Global** scope when state must be shared across disparate topics (e.g., authenticated user context, selected cost center). Over-allocating global variables pollutes the global namespace and risks unintended side-effects during multi-topic redirections.


* **Short-Circuit Condition Ordering:**
* Position the most frequent or computationally lightweight conditions toward the far left of the condition group. Since evaluation occurs sequentially left-to-right, placing high-probability branches first minimizes condition evaluation overhead.


* **Deterministic Fallback Routing:**
* Always provide meaningful logic within the **All other conditions** branch. Never leave the catch-all branch empty if subsequent actions depend on variables configured inside specific condition branches; unhandled execution paths can pass null references downstream.


* **Slot Filling Management:**
* For repetitive operational workflows (e.g., HR service desks checking multiple consecutive employee records), set question behavior to **Ask every time** if the variable must be explicitly re-collected per turn, or explicitly clear the variable via a Power Fx formula node before re-prompting.

## 5. Technical Limitations, Gotchas & Guardrails

* **Choice Entity Creation Gotcha:**
* When adding multiple choice options in the question builder, typing a choice string does **not** register it automatically. Makers must explicitly press **Enter** after each item. Failing to press Enter drops the candidate option before the condition branch is generated.


* **Condition Reordering Constraints:**
* The **All other conditions** branch is structurally anchored as the terminal `Else` node. It cannot be moved leftward, reordered, or deleted from the condition collection.


* **Variable Scope Lock-in:**
* Changing a variable from `Choice` type (Multiple Choice) to `String` (User's Entire Response) breaks existing condition nodes referencing the enum values (`'Topic.employeeName'.Option`). All dependent conditional branches and Power Fx expressions must be updated manually.


* **NLU vs. Multiple Choice UI Buttons:**
* When Multiple Choice is selected, channels that support interactive buttons (e.g., Teams, modern web chat) render quick-select options. However, if a user types a synonym or free text that the NLU cannot unambiguously map to the configured choices, reprompt logic triggers. If retries expire, execution terminates or diverts to Fallback.

## 6. AB-620 Exam Takeaways & Trap Alerts

* **Exam Trap — Topic vs. Global Variable Scope:**
* *Trap:* A scenario asks why Topic B cannot access `employeeName` collected in Topic A.
* *Fact:* Variables default to **Topic scope**. To access a variable across independent topics without passing it as an explicit redirect parameter, the maker must toggle the scope to **Global (any topic can access)**.


* **Exam Trap — Condition Evaluation Direction:**
* Condition nodes evaluate strictly **left-to-right**. If two branches can evaluate to true, **only the leftmost matching branch executes**. The rightmost branches are ignored.


* **Exam Trap — Question Skipping Behavior:**
* Questions configured with *Skip if value exists* will NOT prompt the user if the variable was previously slot-filled in a prior turn or topic. If the exam asks how to force an agent to confirm or re-prompt for an input regardless of prior state, set the property to **Ask every time**.


* **Exam Trap — Variable Sensitivity:**
* Marking a variable as **Sensitive** does not alter its logical evaluation in conditions or formulas; it specifically masks the variable value in application telemetry, conversation transcripts, and diagnostic session logs to prevent PII exposure.


* **Exam Trap — Identification Types:**
* *User's entire response* stores unparsed text as a string without schema validation.
* *Multiple choice options* constrains answers to predefined list items and outputs a typed choice enum that directly spawns canvas condition branches.
